## Decisions, rationale, and invariants

- `NativeReviewController` is host-only; public HTTP and provider messages cannot invoke native acceptance. The host authenticates/authorizes `actorId`; this class is not an authentication mechanism.
- `prepare` consumes persisted passed verification for a completed, still-verified connection. It moves the task through verifying to ready, stores exact native evidence and returns its canonical SHA-256 digest. Reservations remain held.
- `accept` requires actor ID, expected row version, reviewed evidence digest and literal offline classification. It revalidates current connection/evidence/check bindings and immutable object integrity. The accepted deliverable is the reviewed immutable object set, not current mutable workspace contents.
- `Task.nativeQualification` retains connection/runtime/offline scope. Revising work clears it. Existing `Store.accept` rejects native-qualified tasks; native evidence remains separate from simulator evidence schemas.
- Task acceptance, native connection terminal status, reservation release, command result and audit event commit atomically. Duplicate command keys return their original result; changed payloads conflict. Historical acceptance does not rerun the provider or pretend to reverify the current filesystem.
- Accepted connections are excluded from unresolved reservation scans; failed/reconciled/unknown connections cannot enter the acceptance path. Only Store's explicit acceptance transaction should call `ProviderJournal.markAccepted`.
- Generic native report/connection methods remain trusted-host APIs. No live qualification, account authorization, OS containment or paid fallback was added. Schema stays v2; changes use existing JSON bodies and evidence rows.
