## Decisions, rationale, and invariants

- Protocol code is host-driven and does not launch Codex. Only the checked-in
  synthetic Node peer is started by the fixture runner.
- `RpcChannel.beforeWrite` must persist the exact `frame` before resolving. Hook
  failure prevents sending; deadlines also prevent late hooks from sending.
- Outgoing IDs are connection-local. A durable integration must additionally bind
  connection identity, task, attempt, generation, session and work revision.
- The channel remembers attempted/unacknowledged IDs when it closes. Acknowledged
  responses still require host persistence before business-state advancement.
- `CodexLifecycle` models one attempt. Unknown server requests fail closed;
  unhandled notifications are ignored and cannot change state or permissions.
- Only command/file approval denial is implemented. Read-only request policy is
  not proof of OS containment. No approval grants or native tools are executed.
- Successful terminal output remains `result_pending`. The durable controller is
  intentionally unchanged and still accepts only Phase 2 simulator evidence.
- The generated schema version is pinned, not a live G00 qualification. Source
  hashes identify exact exported schema files. See adapter README for regeneration.

## Assumptions made

The host owns the journal and transport callbacks. This slice assumes an explicitly
selected native thread ID; it does not create, attach, resume or authorize a session.
The installed CLI's offline schema generator describes the pinned binary. Zod's
existing converter validates selected schema roots; no full SDK compatibility claim.
