## Decisions, rationale, and invariants

- `NativeVerifier` is a trusted-host offline API. Checks and absolute workspace paths are registered by host code; provider messages cannot supply them. `{ stopped: true }` is a trusted host assertion, not proof gathered by this class. Production lifecycle orchestration must establish it using owned process/session shutdown.
- Only completed `result_pending` connections can enter `verifying`. Native task state remains `needs_attention`; passing checks record connection `verified`, failed checks `verification_failed`, and uncertainty `unknown`. All retain reservations until explicit trusted reconciliation. No native task acceptance is enabled yet.
- Native reports bind task/attempt/work revision, connection/generation, workspace/root hash, host/provider, native session/run, tree/artifact hashes and command hash. Classification is explicitly offline; no simulated labels.
- Snapshots exclude only root `.git`. Limits: 1,024 entries, 16 MiB file bytes, depth 32. Database and objects must reside outside the captured workspace. Check commands must leave the captured tree unchanged. This is not an atomic filesystem snapshot or hostile-process containment.
- Command hash binds executable path, args and cwd, not executable binary contents. The host owns tool qualification. Output/error text is discarded, not evidence.
- File reads reject links/hardlinks/special files and compare metadata around bounded reads. Before/after manifests detect ordinary changes. Do not claim resistance to malicious concurrent mutation/reversion.
- Verification report lives in the existing connection JSON body; no new SQL schema version. References and report commit together; unreferenced objects from interrupted work are retained under existing retention policy. Recovery converts old-generation `verifying` to unknown, without releasing reservations or retrying.
